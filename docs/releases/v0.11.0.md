# RustQueue 0.11.0

RustQueue 0.11.0 adds an optional Linux io_uring storage backend and reduces
buffer copying for large message reads. The backend defaults to off. The v7
storage format, local durability contract and NSQ compatibility remain unchanged.

## Optional io_uring

Enable the backend at Broker startup:

```toml
[storage]
io_uring_enabled = true
```

The environment override is `RUSTQUEUE_IO_URING_ENABLED=true`. Kubernetes uses
Helm `queue.ioUringEnabled` / RustQueue `spec.ioUringEnabled`. Linux 5.10+ and
permission to use io_uring are required; requesting unavailable support fails
startup explicitly. Non-Linux systems continue to work with the setting off.

- Independent coalesced payload ranges can read concurrently. Existing CRC,
  segment-lease, queue, worker and delivery-budget protections remain in place.
  Each batch uses at most 64 reads and 2 MiB of scratch buffers, or one larger body.
- Multiple Channel WALs can sync concurrently for FIN/REQ and TTL discard.
  Durable acknowledgements still wait for all required syncs to finish.
- Single contiguous reads and single-file syncs keep their portable path.
  Network I/O, segment append, metadata, checkpoints and maintenance are unchanged.
- Isolated bodies larger than 2 MiB reuse the verified read buffer, removing
  one large allocation and copy. Smaller bodies keep the previous copy path.
- Startup logs, native Broker stats `io_uring_enabled` and Prometheus
  `rustqueue_io_uring_enabled` report the initialized backend.

Containers may require an administrator-installed seccomp profile permitting
`io_uring_setup`, `io_uring_enter` and `io_uring_register`. The optional Helm
`queue.brokerSeccompProfilePath` / RustQueue `spec.brokerSeccompProfilePath`
selects a node-local profile; leaving it unset preserves `RuntimeDefault`.
See [configuration, bounds and benchmarks](../architecture/io-uring.md).

## Validation and performance boundaries

Local OrbStack validation passed 433 workspace tests and 22 real io_uring
checks, including read corruption/truncation, cancellation, sync errors,
SIGKILL recovery and reopening with the backend disabled. Seven macOS reader
tests passed. Clippy and formatting checks also passed. `make test-io-uring`
runs the actual backend and fails if the environment does not permit it.

Exploratory comparisons used identical durable ACK settings. In 15 alternating
pairs, the final 4 MiB read optimization improved median fetch throughput by
8.2%, while fetch p99 increased from 1.015 ms to 1.146 ms. This retained the Linux
page cache and did not measure publish or FIN latency. Small-message read
throughput was approximately flat. In three short TCP pairs per workload,
single-hot-Topic throughput regressed 18.6%; four-Topic throughput was
approximately flat. All measured deliveries had zero missing or duplicate
messages. These are shared-VM exploratory results, not production qualification
or a general TCP performance claim. io_uring remains opt-in.

The comparison was between the initial and optimized io_uring implementations,
with the backend enabled in both; it was not a 0.10.1-versus-0.11.0 comparison.
The [measurement summary](../../benchmarks/experiments/io-uring-20261028.json)
records the complete final matrix and its limits.

## Upgrade

Apply the updated CRDs before upgrading an existing Operator installation so
the new optional fields are retained. Update Broker, Operator and Console
packages/images to 0.11.0. No Topic data conversion is required. Start with
io_uring disabled, then evaluate it on the deployment's kernel, storage and
workload. Disabling the setting and restarting returns to portable I/O.
