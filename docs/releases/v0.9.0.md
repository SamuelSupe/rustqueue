# RustQueue 0.9.0

RustQueue 0.9.0 adds a Topic-scoped expiration policy for workloads that can
discard a message when no consumer has completed it within a fixed lifetime.
The existing reliable behavior remains the default, and the NSQ wire protocol
and publish acknowledgement contract are unchanged.

## Topic TTL discard

`RustQueueTopic.spec` and the Broker/Console observation models expose:

```yaml
deliveryMode: RELIABLE | TTL_DISCARD
messageTtlSeconds: integer | null
```

- `RELIABLE` is the default and requires `messageTtlSeconds` to be absent.
- `TTL_DISCARD` requires a positive whole-second TTL.
- The TTL starts at the Broker-assigned write timestamp. It is absolute and is
  not restarted by routing, deferral, requeue, redelivery or `TOUCH`.
- Expiration removes the message from the unrouted Topic backlog, durable and
  ephemeral Channels, deferred/requeue state and in-flight state. It does not
  publish a DLQ entry.
- `TTL_DISCARD` retries normally before the deadline and bypasses the
  retention/max-attempt DLQ termination rules. The TTL is its only final
  boundary.
- A delivery reservation and socket handoff recheck the deadline. If a slow or
  blocked socket cannot finish a frame before expiration, the Broker closes
  that consumer connection rather than leaving a partially parseable NSQ
  stream. A frame that was fully written but not `FIN`ed still expires at the
  same absolute deadline; later `FIN`, `REQ` and `TOUCH` receive the normal
  not-in-flight error.
- Logical expiration is immediate at the deadline. Segment files are reclaimed
  later by normal reader-safe GC, so physical disk usage may lag the logical
  discard.

The label-free `rustqueue_ttl_discarded_messages_total` counter is always
available. Optional detailed Topic metrics use the existing bounded series
budget.

## Management and ownership fencing

Topic creation may include the policy. Existing Topics can be changed with the
`CONFIGURE` operation through the Console management flow or the Broker's
authenticated `POST /v1/manage/topics/configure` endpoint. The request carries
the complete policy, including `delivery_mode` and `message_ttl_seconds`.

Enabling TTL or shortening it can immediately discard old backlog according to
the original Broker write timestamp. Such changes require an impact preview
and exact Topic-name confirmation. Extending or disabling TTL affects only
messages that have not already expired and cannot revive discarded data.

Policy changes are rejected while the Topic has multiple visible owners or is
mid-migration. The Console preview and apply challenge bind the operation to
the observed single owner, resource identity, revision and operation ID;
retries preserve the operation identity and completed-owner progress.

The legacy NSQ-compatible `/topic/create` endpoint continues to create a
`RELIABLE` Topic. It does not accept a per-publish TTL. `PUB`, `MPUB` and
`DPUB` continue to acknowledge according to `queue.publish_ack_mode` and do
not wait for a Channel or consumer.

## Compatibility and upgrade from 0.8.4

- Existing and automatically created Topics remain `RELIABLE` unless an
  operator explicitly configures `TTL_DISCARD`.
- Older Topic manifests without the new policy fields load with the reliable
  defaults. No manifest migration is required.
- The on-disk format remains v7. The v7 clean-directory boundary and its
  existing reader/writer compatibility fences remain in force; no storage
  migration is required from 0.8.4.
- NSQ V2 commands, lookup, TLS/mTLS, AUTH, compression, fan-out, ephemeral
  Channels and publish acknowledgement modes retain their existing contract.

For a 0.8.4 to 0.9.0 Kubernetes upgrade, apply the checked-in CRDs before
using the new Topic fields. Helm does not upgrade an already-installed CRD:

```sh
kubectl apply -f deploy/helm/rustqueue/crds
kubectl wait --for=condition=Established \
  crd/rustqueuetopics.rustqueue.io --timeout=60s
helm upgrade rustqueue deploy/helm/rustqueue \
  --namespace rustqueue \
  --set queue.image=registry.example/rustqueue:0.9.0
```

The CRD validation requires `RELIABLE` without a TTL and `TTL_DISCARD` with a
positive `messageTtlSeconds`. Use the Console preview/configure flow for
online policy changes; do not edit a Topic policy while ownership is visibly
migrating. Existing PVCs and v7 data are retained by the normal rollout.
