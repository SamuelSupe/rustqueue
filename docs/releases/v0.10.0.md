# RustQueue 0.10.0

RustQueue 0.10.0 adds an optional best-effort WebSocket receive path for live
consumers of existing `TTL_DISCARD` Topics. Topic TTL discard itself was
introduced in 0.9.0 and remains the prerequisite; this release does not change
the NSQ publish contract, reliable Topics, or v7 storage format.

## WebSocket TTL live subscription

When enabled, each Broker's existing HTTP listener accepts one Topic per
connection:

```text
GET /v1/ws/topics/{topic}
Sec-WebSocket-Protocol: rustqueue.live.v1
```

The Topic must already exist on that Broker and use `deliveryMode=TTL_DISCARD`.
The endpoint never creates a Topic. Unknown Topics and `RELIABLE` Topics are
rejected. A client first calls Discovery `/lookup`, then connects directly to
every healthy Broker owner returned for that Topic; the producer proxy does
not multiplex this path. A client may union owner streams and deduplicate
migration overlap using the broker-scoped message ID in each frame.

The stream starts at the current Topic tail. Messages published before the
connection, during disconnection, or after a failed write are not replayed.
There is no WebSocket ACK, reconnect resume, or WebSocket-layer retry. A
complete frame write means only that RustQueue finished the socket write; it is
not a business processing acknowledgement.

### Ready boundary

The HTTP `101 Switching Protocols` response establishes only the transport.
The live subscription begins when the server sends the text control frame
`{"type":"ready",...}`. No message capture is promised before `ready`,
including while the server has sent `auth_required` and is waiting for the
client's `auth` control. Clients must not treat HTTP upgrade or
`auth_required` as the capture boundary.

The `ready` payload identifies the Topic and subscription, and uses
`{"start":"tail","ack":"auto"}` to make the current-tail and automatic
post-write completion semantics explicit.

Before `ready`, text controls are used for authentication. After `ready`, the
server sends complete binary data frames and may send terminal error controls.
The server may also send WebSocket Ping frames; clients should answer using
the standard WebSocket Pong behavior.

### Binary data frame

Each message is exactly one complete binary WebSocket frame. The first 24 bytes
are big-endian metadata followed by the original message body:

| Offset | Size | Field |
| --- | ---: | --- |
| `0..4` | 4 | ASCII magic `RQW1` |
| `4..6` | 2 | Header length, fixed at `24` |
| `6..8` | 2 | Delivery attempts, unsigned `u16` |
| `8..16` | 8 | Broker timestamp, signed `i64` nanoseconds |
| `16..24` | 8 | Broker-scoped message ID, unsigned `u64` |
| `24..` | — | Original message body |

### AUTH, Origin and errors

WebSocket AUTH reuses the existing subscription permission with the virtual
Channel `websocket#ephemeral`. Service clients may send
`Authorization: Bearer <token>` during the HTTP upgrade. Browser clients can
complete the `auth_required` / `auth` text-control exchange. Credentials must
never be placed in a query parameter, and query parameters are rejected.

Browser requests with an `Origin` header must exactly match
`websocket.allowed_origins`; a missing Origin is accepted for a non-browser
client but still requires normal authentication. Discovery's read-only
`/lookup` response uses the same allowed-origin policy.

Handshake failures reuse the HTTP `ApiError` shape: the stable code is in the
JSON `message` field and the explanation is in `detail`. After upgrade,
terminal errors use a text control such as
`{"type":"error","code":"E_TOPIC_CLOSED","detail":"..."}` before the
connection closes:

| Code | Meaning |
| --- | --- |
| `E_WS_QUERY_FORBIDDEN` | Query parameters are forbidden; use the path and headers. |
| `E_WS_ORIGIN` | Browser Origin is not an exact configured allowlist entry. |
| `E_WS_SUBPROTOCOL` | `rustqueue.live.v1` was not negotiated. |
| `E_BAD_TOPIC` | Topic does not exist on this Broker. |
| `E_WS_TTL_REQUIRED` | Existing Topic is not `TTL_DISCARD` or changed away from it. |
| `E_WS_CAPACITY` | Connection, Channel or frame-memory capacity is exhausted; back off. |
| `E_WS_CONTROL` | Unsupported client text/binary data frame was received. |
| `E_WS_HEARTBEAT` | Peer missed the heartbeat liveness window; reconnect. |
| `E_AUTH_TIMEOUT` | `auth` was not received before the AUTH deadline. |
| `E_BAD_AUTH` | AUTH control was non-text, malformed, or missing a valid `auth`/`secret`. |
| `E_AUTH_OVERLOADED` | AUTH service or capacity gate is exhausted; retry later. |
| `E_AUTH_FAILED` | Authentication service or credential validation failed. |
| `E_UNAUTHORIZED` | AUTH does not permit the Topic subscription. |
| `E_TOPIC_CLOSED` | Topic was deleted, tombstoned, or closed. |
| `E_OWNER_CHANGED` | Topic owner/fence changed; perform a fresh lookup. |
| `E_DRAINING` | Broker is draining and closes the live subscription. |
| `E_SHUTDOWN` | Broker is shutting down; reconnect after discovery. |

### Capacity, TTL and close semantics

The feature is default-off and uses bounded runtime defaults:

```toml
[websocket]
enabled = false
max_connections = 1024
max_connections_per_topic = 256
frame_inflight_bytes = 134217728
allowed_origins = []
```

Each connection creates one ephemeral Channel and reserves at most one message.
If the global frame budget, total connection limit, per-Topic limit or Channel
limit is exhausted, admission fails closed with `E_WS_CAPACITY`. A failed,
cancelled or timed-out write releases the reservation and closes the
connection; RustQueue does not retry the frame over WebSocket.

The write deadline is the smaller of the existing socket timeout and the
message's remaining absolute TTL. If a complete frame cannot be written before
that deadline, the connection closes rather than leaving a partial frame. TTL
changes take effect for subsequent deadline checks. Paused Topics stop taking
messages. Topic deletion, owner migration, a change to `RELIABLE`, Broker
draining, shutdown and heartbeat timeout close affected connections so the
client can discover a healthy owner again.

The aggregate metrics include WebSocket connections, completed messages and
bytes, authentication failures, capacity rejections, slow-consumer closes and
non-TTL Topic rejections. `/v1/capabilities` advertises
`websocket_ttl_live_v1` for binaries that implement this protocol.

## Kubernetes configuration

The runtime `[websocket]` settings are exposed equivalently through Helm
`queue.websocket` values and the RustQueue Operator/CRD `websocket` spec:

```sh
helm upgrade rustqueue deploy/helm/rustqueue \
  --namespace rustqueue --reuse-values \
  --set queue.websocket.enabled=true \
  --set queue.websocket.maxConnections=1024 \
  --set queue.websocket.maxConnectionsPerTopic=256 \
  --set queue.websocket.frameInflightBytes=134217728 \
  --set-string 'queue.websocket.allowedOrigins[0]=https://app.example'
```

The equivalent Operator/CRD fragment is:

```yaml
spec:
  websocket:
    enabled: true
    maxConnections: 1024
    maxConnectionsPerTopic: 256
    frameInflightBytes: 134217728
    allowedOrigins:
      - https://app.example
```

The existing Broker HTTP Service and NetworkPolicy are reused. The chart adds
no port and no default Ingress for this feature. Keep the Origin allowlist
narrow and put external browser access behind the deployment's normal TLS and
authentication boundary. Apply the checked-in CRDs before using new WebSocket
fields on a cluster where the CRDs are already installed; Helm does not
upgrade an existing CRD automatically.

## Upgrade from 0.9.0

No Topic data migration is required. Existing Topics retain their persisted
policy, and WebSocket support remains disabled unless explicitly enabled. The
NSQ TCP/HTTP endpoints, publish acknowledgement modes, Topic TTL semantics and
v7 storage compatibility remain unchanged.

For a Kubernetes rollout, update the CRDs first, then roll the 0.10.0 image:

```sh
kubectl apply -f deploy/helm/rustqueue/crds
kubectl wait --for=condition=Established \
  crd/rustqueuetopics.rustqueue.io --timeout=60s
helm upgrade rustqueue deploy/helm/rustqueue \
  --namespace rustqueue \
  --set queue.image=registry.example/rustqueue:0.10.0
```

After the Broker fleet is Ready, enable the `queue.websocket` settings in a
separate change if live subscriptions are needed. Consumers should continue
to use `/lookup` and direct owner connections; they must not assume a single
Broker or a replay window during rollout. A 0.9.0 binary that does not
advertise `websocket_ttl_live_v1` simply keeps the optional endpoint
unavailable while the existing NSQ and TTL paths continue to work.

Every 0.10.0 release contains the following five assets:
